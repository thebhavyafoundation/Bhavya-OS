# Project Constitution

**Document:** 12 | **Version:** 1.0 | **Effective:** 2026-08-07 | **Status:** Constitutional

---

## Preamble

This document establishes the portfolio-first education model of the Bhavya AI Institute. Every course must culminate in production-grade work. Students graduate with evidence of ability, not certificates alone.

---

## Article 1: Project Philosophy

### 1.1 Core Principle

**"Students graduate with evidence of ability, not certificates alone."**

Every project must be:

1. **Real** — Solves a real problem
2. **Complete** — End-to-end implementation
3. **Deployed** — Running in production
4. **Documented** — Clear documentation
5. **Presented** — Demonstrated to others

### 1.2 Project Tiers

| Tier           | Duration   | Complexity  | Example                     |
| -------------- | ---------- | ----------- | --------------------------- |
| Lab            | 1-2 hours  | Guided      | Implement linear regression |
| Mini Project   | 1-2 weeks  | Semi-guided | Build a chatbot             |
| Course Project | 2-4 weeks  | Independent | Build a RAG system          |
| Capstone       | 4-8 weeks  | Open-ended  | Build an AI SaaS            |
| Research       | 8-16 weeks | Original    | Publish a paper             |

---

## Article 2: Project Requirements

### 2.1 Every Project Must

1. **Solve a real problem** — Not toy examples
2. **Use real data** — Not synthetic datasets
3. **Be deployed** — Running in production
4. **Have documentation** — README, architecture, decisions
5. **Have tests** — Unit, integration, E2E
6. **Be version controlled** — Git repository
7. **Be presentable** — Demo, portfolio entry
8. **Be reproducible** — Others can run it

### 2.2 Project Types

| Type           | Purpose              | Assessment            |
| -------------- | -------------------- | --------------------- |
| Lab            | Practice concepts    | Completion            |
| Mini Project   | Apply skills         | Quality, completeness |
| Course Project | Integrate knowledge  | Production readiness  |
| Capstone       | Demonstrate mastery  | Impact, quality       |
| Research       | Contribute knowledge | Novelty, rigor        |

## Article 4: Project Assessment

### 4.1 Assessment Criteria

| Criterion          | Weight | Description                                   |
| ------------------ | ------ | --------------------------------------------- |
| Problem Definition | 15%    | Clear problem statement, real-world relevance |
| Solution Design    | 20%    | Architecture, technology choices, scalability |
| Implementation     | 25%    | Code quality, best practices, functionality   |
| Evaluation         | 15%    | Metrics, testing, comparison                  |
| Documentation      | 10%    | README, architecture, decisions               |
| Presentation       | 5%     | Demo, communication, clarity                  |
| Impact             | 10%    | Users, contributions, real-world use          |

### 4.2 Scoring Rubric

| Score  | Description                                        |
| ------ | -------------------------------------------------- |
| 90-100 | Exceptional: Production-ready, impact demonstrated |
| 80-89  | Strong: Complete, deployed, well-documented        |
| 70-79  | Satisfactory: Working, basic documentation         |
| 60-69  | Developing: Partially complete, needs improvement  |
| <60    | Incomplete: Significant gaps, needs major revision |

### 4.3 Validation Process

1. **Automated Testing** — Code correctness, tests pass
2. **Deployment Check** — Running in production
3. **Peer Review** — Code review by peers
4. **Mentor Review** — Quality assessment by mentor
5. **Defense** — Oral presentation and Q&A

## Article 5: Project Portfolio

### 5.1 Portfolio Requirements

Every student must maintain a portfolio containing:

1. **All projects** — Labs, mini projects, course projects
2. **Capstone** — Major project
3. **Research** — Papers, publications
4. **Open Source** — Contributions, maintained projects
5. **Blog Posts** — Technical writing
6. **Presentations** — Talks, demos

### 5.2 Portfolio Format

```
portfolio/
├── README.md
├── projects/
│   ├── lab-1/
│   ├── mini-project-1/
│   ├── course-project-1/
│   ├── capstone/
│   └── research/
├── open-source/
│   ├── contributions/
│   └── maintained/
├── blog/
│   ├── post-1.md
│   └── post-2.md
└── presentations/
    ├── talk-1/
    └── talk-2/
```

### 5.3 Portfolio Validation

Portfolio must demonstrate:

1. **Breadth** — Multiple domains covered
2. **Depth** — At least one deep specialization
3. **Quality** — Production-grade work
4. **Impact** — Real-world use
5. **Growth** — Progression over time
